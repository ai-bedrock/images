# decisions

This repo's internals: what, why, what a change would cost. `by: lead` for the lead's calls, `by: ai` for the rest until the lead weighs in.

- by: lead. Images live in their own public repo, one folder per image (roles later build `FROM` coreos); nothing revealing in it.
- by: lead. Images are signed.
- by: ai. A sigstore key pair signs every pushed tag (`podman push --sign-by-sigstore-private-key`, signatures as sigstore attachments); private key and passphrase are repo secrets. Keyed, not keyless: containers/image policies match Fulcio identities by email only, and GitHub Actions certificates carry a workflow URI. Change: keyless once URIs match (later.md).
- by: ai. coreos's `policy.json` requires that signature for the whole `ghcr.io/ai-bedrock` namespace and accepts anything else unchecked, so Fedora's and third-party images pull as before; the accept-anything is written per transport (docker, docker-daemon, containers-storage, oci, oci-archive, docker-archive, dir) under a `reject` default, because bootc (ostree-ext) refuses `ostree-image-signed` references while the default is `insecureAcceptAnything`. Hosts run the signature-checked reference `ostree-image-signed:docker://ghcr.io/ai-bedrock/coreos:stable`, so bootc's daily updates are checked too. Change: narrow or widen the scope in one file.
- by: ai. CI is podman only (the containers tools CoreOS uses, from the runner): one reusable `build.yml`, one small caller per image with its path filter; a scheduled run builds only when the base's digest has no `base-<digest>` tag yet, so an unchanged image doesn't reboot hosts. Each build is pulled back through coreos's policy. Checks on `ubuntu-slim`, builds on `ubuntu-26.04` (x86_64).
- by: ai. coreos updates through bootc's own `bootc-fetch-apply-updates.timer` in a daily window (03:30 UTC plus up to 30 minutes), Zincati off: Zincati follows Fedora's update graph, not a registry tag. `bootc upgrade --apply` reboots only when a new image was staged and keeps the previous deployment for rollback.
- by: ai. coreos's host firewall is nftables in its own `inet host` table (policy drop; ICMP, DHCP replies, TCP 22, 80, 443), and nothing but sshd listens on the host itself (LLMNR and mDNS off); 80 and 443 are for a web server in a container.
- by: ai. nginx builds on nginx's official unprivileged Alpine image at a pinned stable tag (`1.30.5-alpine3.24`) and adds nginx's own ACME module (`nginx-module-acme` from nginx.org's signed Alpine repository, the version matching the base's nginx): certificates are ordered and renewed inside nginx, no certbot, cron or reload hook. Why Alpine: nginx.org ships the module there as a package, and the image is a third of the Debian one. Change: bump the tag by hand for a new nginx (the daily build follows the tag's rebuilds).
- by: ai. nginx's config is a template the base image's entrypoint fills from the environment (server name, ACME directory), so no value specific to a deployment is in the image; no contact address and no external account binding (Let's Encrypt needs neither). The site is not in the image: nginx serves whatever is mounted at `/usr/share/nginx/html` (the `site` image, below).
- by: ai. nginx's HTTPS: one server for the apex and www with one certificate for both (www 301s to the apex; HTTP 301s to HTTPS, ACME challenges excepted), HSTS a year (subdomains and preload: the lead's line below), a CSP allowing only same-origin images and styles (no scripts, no inline styles), `frame-ancestors 'none'`, `nosniff`, `strict-origin-when-cross-origin`, `Cross-Origin-Opener-Policy: same-origin`. The ACME account key, the certificate and its key live in `/var/lib/nginx/acme`, a volume, so a restart reuses them; a lost volume just orders a new certificate.
- by: ai. The placeholder is a real page that search engines may index: 200, title, description, canonical, robots.txt allowing all, a sitemap, a 404 page with status 404 (the only `noindex`), no "coming soon". Change: replace `site/public/`.
- by: lead. After the first boot nothing on a host reaches the cloud's metadata service, since the user-data it serves may carry a secret that couldn't come in any other way.
- by: ai. coreos rejects 169.254.169.254 and fe80::a9fe:a9fe (OpenStack's IPv6 metadata address) in its own table's output chain (the host, and rootless containers, whose pasta traffic leaves from the host) and forward chain (rootful containers); reject, not drop, so a client fails at once instead of hanging a boot. Ignition fetches the user-data before this image is booted (a stock first boot, then the rebase), so it is unaffected. What else read the metadata service after Ignition: only `afterburn-sshkeys@core` (each boot, OpenStack and most clouds); it is off (a drop-in condition on an `afterburn.sshkeys` kernel argument nobody sets, which skips it and keeps its target satisfied), the keys come from Ignition. Afterburn's check-in units don't run on OpenStack; the hostname is Ignition's `/etc/hostname`. Change: drop the rules and the drop-in.
- by: lead. The site's files are their own image, split from nginx, and CI tells the host to update right after a signed push, naming the image(s) it pushed.
- by: ai. The push trigger is SSH to a `deploy` user whose only possible command is a forced one (sshd `Match User deploy`: `ForceCommand`, keys only from root-owned `/etc/image-update/authorized_keys`, no pty, forwarding, tunnel or rc; the key line also says `restrict,command=`). The command accepts only lower-case names separated by single spaces, compares each literally with the host's list (`/etc/image-update/images`, from Ignition), refuses the whole request otherwise (exit 2, logged), and starts `image-update@<name>.service` through a polkit rule that allows the deploy user that start and nothing else; that root unit pulls the image through the signature policy, restarts the units listed with it only if it changed, and echoes `<name> <digest> <what it did>` back. Why: no inbound port besides SSH, no daemon, no sudo, and the root side never sees the client's text beyond a name it looked up. Polling the registry every minute would need no key and no user at all, but is not a push trigger (the lead's call). `image-update.timer` pulls every listed image daily (00:30 UTC) in case a trigger was missed, since `podman auto-update` doesn't follow an image mounted into a container. Change: drop the user, rule, units and the Match block.
- by: ai. `site` is `FROM scratch` with only the files (tens of kB), mounted read-only into nginx as an image mount; its workflow has no schedule (no base to follow). The site and nginx workflows each deploy the one image they built, named in the trigger; coreos isn't deployed that way (bootc's own timer reboots in its window). Deploy secrets (`DEPLOY_HOST`, `DEPLOY_KNOWN_HOSTS`, `DEPLOY_SSH_KEY`) are repo secrets, so the host's name never lands in a public file or log (masked, with its resolved addresses); the host key is pinned, never trust-on-first-use. Change: one more secret set per host, or a GitHub environment when there are several.
- by: ai. coreos hardens in place, no reinstall: sshd sets its own crypto ahead of Fedora's crypto policy (`mlkem768x25519-sha256` and X25519 key exchange, ChaCha20 and AES-GCM, encrypt-then-MAC MACs, the ed25519 host key only; every current OpenSSH client and CI's runner speak them), turns off agent, remote and socket forwarding, compression and rc files (local `-L` stays for the admin's tunnels), drops dead clients after 10 minutes, logs key fingerprints, and closes deploy connections that open no session after 30 s. Change: one file, `10-hardening.conf`.
- by: ai. SSH brute force is limited twice: sshd's own per-source penalties (OpenSSH 10's defaults) and an nftables per-address limit on new SSH connections (15 a minute, bursts of 30, then dropped until the rate falls), which a login or a CI deploy never reaches. No fail2ban: nothing to install on an image-based host, and the kernel limit needs no log parsing. Change: the two rules in `nftables.conf`.
- by: ai. The firewall is reloaded with `nft -f /etc/sysconfig/nftables.conf` only (its `destroy table` swaps only this table), never `systemctl reload|restart nftables`: Fedora's unit flushes the whole ruleset, podman's netavark table with it, which cuts the published ports until the container restarts. Change: none needed; a boot loads it before podman.
- by: ai. Kernel sysctls on top of Fedora's (`90-hardening.conf`): no ICMP redirects in or out, `kptr_restrict=1`, `yama.ptrace_scope=1`, `suid_dumpable=0`, `bpf_jit_harden=2`, `kexec_load_disabled=1`; rp_filter stays loose (Fedora's 2) for container routing. Zincati is disabled, not only configured off. Change: delete the file; re-enable the unit.
- by: ai. A host changed in place gets byte-identical copies of the image's changed `/etc` files (same content, mode and label), so after the next image update ostree sees them as unmodified and later image changes merge again. Change: none.
- by: ai. nginx's TLS 1.2 allows only ECDHE with AES-GCM or ChaCha20 (Mozilla's intermediate list), no session tickets; slow clients time out after 10 s; a `Permissions-Policy` denies camera, microphone, geolocation, payment and USB. No `Cross-Origin-Resource-Policy`: it would stop other sites from using the site's images. Change: the template.
- by: lead. HSTS covers every subdomain and asks for preloading: `max-age=31536000; includeSubDomains; preload`, sent by the HTTPS server (the apex's pages and the www redirect; plain HTTP can't carry it). No hstspreload.org submission: `.dev` is preloaded as a whole TLD. Every subdomain must serve HTTPS from then on. Change: the template's header.
- by: ai. nginx is tested in CI before its push (`nginx/test.sh`, the build workflow's Test step runs any image folder's `test.sh`): pebble (`ghcr.io/letsencrypt/pebble`, a pinned release) on a throwaway podman network, whose DNS resolves the test names (`example.test`, `www.example.test`) to the nginx container as network aliases, so no DNS test server; nginx trusts pebble's test CA through a bundle mounted over its system CA file (the ACME module uses the system trust by default), so the image and template stay unchanged; the client is the image's own curl, trusting only pebble's roots. Change: one script.
